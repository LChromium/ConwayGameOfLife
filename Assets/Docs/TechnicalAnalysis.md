# 技术分析

Conway's Game of Life 的规则本身只有两句话，真正的工程问题在于：**如何保证规则实现正确**，以及**如何在可接受的时间内推进尽可能多的世代**。本文围绕这两点展开。

---

## 1. 规则与计算模型

### 1.1 规则定义

生命游戏是二维二值元胞自动机。每个细胞的状态由"上一代"的 8 邻域决定：

| 当前状态 | 活邻居数 | 下一状态 | 名称 |
|---|---|---|---|
| 死 | 3 | **活** | 诞生 (Birth) |
| 活 | 2 或 3 | **活** | 存活 (Survival) |
| 活 | 0、1 | 死 | 孤独 |
| 活 | 4–8 | 死 | 拥挤 |

记作 **B3/S23**。注意"活 + 2 邻居"与"活 + 3 邻居"都是存活，因此判定式可合并为：

```
next_alive = (neighbours == 3) || (alive && neighbours == 2)
```

这正是 `LifeSimulation.Step()` 中使用的形式。

### 1.2 同步更新（Double Buffering）——最容易写错的地方

所有细胞必须**同时**基于同一代数据计算。若原地更新，先算完的细胞会污染后算细胞所读到的邻居值，产生难以察觉的错误。

因此本实现使用两块缓冲区：读 `current`、写 `next`，整代算完后交换引用。

```csharp
(current, next) = (next, current);   // 元组交换，交换的是引用，不是数据
```

工程上的关键收益：**每代零堆分配**。若每代 `new byte[]`，1024×1024 的棋盘每代要分配 1 MB，GC 压力会直接体现在帧时间抖动上。这里缓冲区只分配一次并复用。

### 1.3 边界条件

| 模式 | 语义 | 实现 |
|---|---|---|
| 固定边界 | 网格外视为永久死亡 | 越界邻居直接跳过 |
| 环绕边界 | 环形拓扑，对边相接 | `(n + size) % size` |

两者对同一个盘面会产生不同演化结果，测试 `WrapEdges_ProducesDifferentResultFromFixedBoundary` 对此做了断言。

## 2. 数据结构选型

### 2.1 为什么用 `byte[]` 而不是 `bool[,]`

| 方案 | 内存 / 格 | 邻居读取 | 说明 |
|---|---|---|---|
| `bool[,]` | 1 B | 多维索引，边界检查开销较大 | C# 中 `bool` 实际占 1 字节 |
| `bool[]`（手动索引）| 1 B | `y*W+x` | 与 `byte[]` 等价 |
| **`byte[]`（本实现）** | **1 B** | `y*W+x`，一维连续 | 可整块 `Array.Clear`，便于后续向量化 |
| `BitArray` / 位平面 | 1/8 B | 需要移位与掩码 | 内存减少 8 倍，但单格读写变慢 |

选择 `byte[]` 的理由：**为后续优化留路**。一维连续数组可被 JIT 边界检查消除（BCE）优化、可被 SIMD 向量化、也可整块内存复制。当前实现尚未用到位打包，但数据布局不阻碍这一步。

索引统一为 `y * Width + x`——**行主序**。这意味着同一行的细胞在内存中相邻，遍历时缓存局部性最好。`Step()` 的循环外层是 `y`、内层是 `x`，与内存布局一致。

### 2.2 为什么 `LifeSimulation` 不依赖 `UnityEngine`

`LifeSimulation.cs` 只 `using System;`。带来的实际好处：

1. **可在 Unity 之外运行**。本仓库的 `.verify/` 工程直接链接这份源码，用 `dotnet run` 做基准测试与规则校验，无需启动编辑器（启动 Unity 做一次基准测量是分钟级的，`dotnet run` 是秒级的）。
2. **EditMode 测试运行快且稳定**。23 个测试总耗时约 0.1 秒，没有场景加载、没有帧循环。
3. **职责清晰**：规则引擎是纯函数式的状态机，表现层（UI Toolkit）与它解耦。

这条边界是刻意设计的，不是偶然结果。

## 3. 样本（Pattern）的正确性来源

题目要求"两种稳定、两种振荡、两种循环震荡"。样本本身是数据，但**数据也会错**——这一点在本项目中真实发生过，值得记录下来。

### 3.1 一次真实的纠错

最初凭记忆手写了脉冲星（Pulsar）的坐标，并用自制的探针程序测量周期。结果：

```
[FAIL] PULSAR (candidate)  pop 28  UNEXPECTED: declared period 3, measured none
```

也就是说，那串坐标**根本不是脉冲星**——它演化到别的东西上去了，40 代内没有回到初态。

随后做了两件事：

1. **先验证测量工具本身**。写了一份独立的 B3/S23 参考实现，在 400 个随机盘面（含 1×1 到 12×12 各种尺寸、两种边界）上与 `LifeSimulation.Step()` 逐格比对——**0 处不一致**。这排除了"引擎有 bug 导致测不出周期"的可能。
2. **不靠记忆，改用权威 RLE**。从 [copy.sh/life](https://copy.sh/life/) 取得标准 RLE，写了个 RLE 解码器（`.verify/Rle.cs`）来生成坐标，而不是手工转录。

结果：

```
[OK] PULSAR          cells= 48 period=3  (expected 3)   populations: 48,56,72,48,...
[OK] PENTADECATHLON  cells= 12 period=15 (expected 15)  populations: 12,22,18,40,...
```

48 个细胞、周期 3、种群在 48→56→72 之间循环——与脉冲星的已知特征完全吻合。

> **教训**：当测量结果与预期不符时，先怀疑被测对象、再怀疑测量工具，最后才怀疑"预期"本身。而验证测量工具的办法，是用一个**独立实现**去交叉验证，而不是重复运行同一个实现。

### 3.2 样本集与展示分组

> **重要说明：下表的"分类"是本项目为展示而作的分组，不是题目的标准定义。**
> 题目只要求"两种稳定状态、两种振荡状态、两种循环震荡状态"，并未定义这三类之间的边界。生命游戏的术语体系中，周期 2 与周期 3 的图样**都属于"振荡器"**，并不构成两个互斥的类别。此处按周期长度分组，是为了让界面能把不同时间尺度的行为并列展示；它诚实地对应到代码中的枚举，但**不应被理解为对题目的权威解释**。

| 样本 | 本项目分组 | 周期 | 细胞数 | 首代种群序列 |
|---|---|---|---|---|
| 方块 BLOCK | 稳定状态 | 1 | 4 | 4,4,4,... |
| 蜂巢 BEEHIVE | 稳定状态 | 1 | 6 | 6,6,6,... |
| 闪烁器 BLINKER | 振荡（周期 2）| 2 | 3 | 3,3,...（形态在横竖间切换）|
| 蟾蜍 TOAD | 振荡（周期 2）| 2 | 6 | 6,6,... |
| 脉冲星 PULSAR | 长周期振荡（周期 3）| 3 | 48 | 48,56,72,48,... |
| 十五周期振荡器 PENTADECATHLON | 长周期振荡（周期 15）| 15 | 12 | 12,22,18,40,18,... |
| 滑翔机 GLIDER | 周期平移（飞船）| 4 | 5 | 平移 (1,1)/周期 |
| 轻型飞船 LWSS | 周期平移（飞船）| 4 | 9 | 平移 (−2,0)/周期 |

**无论采用哪种读法，题目要求都被满足**：存在 2 个完全不变化的图样、2 个周期 2 的振荡图样、2 个周期 ≥3 的原地振荡图样，另有 2 个周期性平移的飞船。全部 8 个样本的行为均由测试断言。

代码中的枚举 `StillLife / Oscillator(周期2) / PeriodicOscillator(周期≥3) / Spaceship` 与上表一一对应。测试 `EveryPattern_HasCellsAndConsistentPeriod` 强制"枚举值 ↔ 周期"的一致性成立，使这份分组不会与实际行为脱节。

### 3.3 判定振荡器与飞船的正确方式

两者都"周期性复原"，但飞船整体平移。判定必须基于**完整活细胞集合**，而不是任何间接指标：

- **振荡器**：经过恰好 `Period` 代后，绝对坐标下的棋盘状态与初始**逐格相同**；且在任何更小的代数上都不相同（否则"周期 N"是假的）。
- **飞船**：经过恰好 `Period` 代后，完整活细胞集合等于初始集合**整体平移同一个偏移量**；关键是要求该周期是**首次**复现——比较**归一化后的形状**（包围盒裁剪掩码）。

> **飞船为什么不能用"是否回到原位"判提前复现**：飞船永远不回原位，所以那条断言恒为真，等于没有判定。把 LWSS 的周期从 4 错写成 8 时，只有"归一化形状首次复现于第 4 代"才能发现。该反例本身也是一项测试（`SpaceshipPeriodCheck_RejectsAMisdeclaredPeriod`）。

判定式写作集合比较：

```csharp
// 振荡器
Assert.AreEqual(initialSnapshot, Snapshot(sim));           // 绝对坐标逐格相同

// 飞船：先求首元素的位移，再要求整个集合按同一位移复原
LifeSimulationTests.AssertSameCells(initial, after, dx, dy, pattern.EnglishName);
```

**曾经采用过两种错误的判定，均已废弃：**

1. *"振荡器每代包围盒中心不变"* —— 这只是当前样本的巧合性质，**不是振荡器的必要条件**。一个包围盒中心缓慢漂移的振荡器（例如在环面上漂移的图样）会因此被误判。它是充分条件之外的多余约束。
2. *"飞船只需细胞数与包围盒位置变化"* —— 太弱：一个**改变形状**的图样只要数量与包围盒移动了就能通过。

`AssertSameCells` 同时断言细胞数相等**且**每个细胞平移后都落在活细胞上，配合等数量，即证明集合完全相同。

## 4. 复杂度分析

设棋盘宽 `W`、高 `H`。

| 操作 | 时间复杂度 | 空间复杂度 | 说明 |
|---|---|---|---|
| `Step()` | O(W·H) | O(1) 额外 | 每格固定读 8 邻居，与棋盘大小无关 |
| `IsAlive` / `SetCell` | O(1) | — | 一次数组索引 |
| `LoadCentered` | O(n + W·H) | O(1) | n 为样本细胞数；`Clear()` 是 O(W·H) |
| `Randomize` | O(W·H) | — | 每格一次随机数 |
| 整块缓冲区 | — | O(W·H) | 两块 `byte[]` |

**核心结论：`Step()` 是 O(W·H)，且每格的常数因子固定为 8 次邻居读取。** 也就是说，总工作量 = 格子数 × 世代数，与细胞密度无关。这是朴素实现的固有特性——包括大量死细胞也在被遍历。

`Step()` 每格的实际操作序列：

```
1 次邻居循环（8 次迭代）
  ├─ 边界处理（取模或跳过）
  ├─ 1 次索引计算 y*W+x
  └─ 1 次数组读取
1 次自身状态读取
1 次规则判定
1 次写入 + 1 次累加
```

值得注意的开销：**环绕边界的取模运算**。`%` 在 x86 上是几十个周期的整数除法，代价远高于一次数组读取。实测数据印证了这一点（见下节）。

运行时为 **Unity Editor 6000.6.0f1 / PlayMode**——**不是独立 Player 构建**。

```
[perf-microbench] SYNTHETIC micro-benchmark - NOT real-time gameplay.
  2000 synchronous Update() calls advanced ~2100-3000 generations in ~300-760 ms
  => 0.14-0.23 ms/generation
```

> **不要引用单一的精确值。** 同一测试在多次运行中给出 0.1445 / 0.1636 / 0.1723 / 0.2264 ms/代，
> 取决于当次推进的代数与机器负载。**该测试每次运行的日志行才是权威出处**；
> 任何引用都应带上是哪一次运行。本文档只给出量级区间。

**这是人工调用微基准，不是真实运行时表现。** 两点偏差必须说明：

1. 循环在**同一帧内**同步调用 `Update()` 2000 次，每次都复用该帧同一个 `unscaledDeltaTime`；真实玩家每帧只调用一次。
2. 经 `SendMessage` 调用，每次多一层反射派发开销。

因此它只回答"规则推进一次的大致成本量级"，**不能**用于描述实时性能。

**真实跨帧的时钟行为**由 `Clock_RunsAtTheRequestedRateAcrossRealFrames` 单独测量：
请求 20 代/秒、跨真实帧运行约 2 秒，实测达成 **≈20.0 代/秒**。该测试验证的是
"时钟确实按请求速率推进棋盘"，不是吞吐上限。

### 5.4 结果：真实 Player 构建，暂停 vs 演化中

**数据出处**：[`Screenshots/player-measurements.jsonl`](../../Screenshots/player-measurements.jsonl)。
开发版 Windows Player，每个场景采样 **240 个真实帧**，**帧率上限 120**、关闭垂直同步
（`targetFrameRate` / `vSyncCount` 均记录在数据中）。下表数值直接取自该文件，不引用其他运行。

**两个场景分别测量、不合并平均**——暂停场景不做规则推进、不触发网格重绘，
把它混进演化场景只会让数字好看：

| 分辨率 | 暂停 平均帧 | 演化中 平均帧 | 差值 | 演化中推进 | 达成速率 | 最差帧（暂停/演化）|
|---|---|---|---|---|---|---|
| 1280×720 | 8.46 ms | 10.86 ms | +2.40 ms | 52 代 | 19.94 代/秒 | 36.7 / 22.0 ms |
| 1920×1080 | 8.48 ms | 10.75 ms | +2.27 ms | 51 代 | 19.76 代/秒 | 40.2 / 23.4 ms |
| 600×1000（竖屏）| 8.65 ms | 10.55 ms | +1.91 ms | 50 代 | 19.74 代/秒 | 48.9 / 22.6 ms |

**采样前先对每个分辨率做一次热身运行**并丢弃。原因是一次未热身的竖屏运行记录到
`pausedWorstMs = 86946`（即单帧 86.9 秒），把该场景均值抬到 370 ms。随后两次独立重跑
分别得到暂停 8.50 / 8.44 ms，**不复现**。

> **关于该异常**：只能说"**原因未知，后续运行未复现**"。把它归因为"首次启动的一次性开销"
> 是超出证据的推断——没有定位到根因，也没有解释 86.9 秒这一量级。
> 该记录保留在 T15，未作解释。热身后的数据即上表。

**这些数字能证明什么**：

1. 采样期间棋盘**确实在演化**——`runningGenerationsAdvanced` 记录起止世代差（52/51/50），
   暂停场景为 **0**。这是先前缺失的证据：早先的 Player 采样测的是暂停界面。
2. 时钟按请求速率工作：请求 20 代/秒，三个分辨率实测 19.94 / 19.76 / 19.74 代/秒。
3. 该开发版在这些场景下平均帧约 **10.6–10.9 ms（演化中）／ 8.5–8.6 ms（暂停）**。
   **最差帧必须分场景看**：在这几次采样中，暂停场景的最大帧间隔（36.7–48.9 ms）
   反而**大于**演化场景（22–23 ms）。仅此而已——**原因未定位，也不能据此推断与演化无关**。

**这些数字不能证明什么**：

- **不能**当作"一帧的计算成本"。`Time.unscaledDeltaTime` 是**帧间隔**，包含呈现、限帧
  等待与空闲时间。
- **不能**把"演化中比暂停多出的约 2 ms/帧"折算成每代成本。
  > 此处曾写"每帧约 0.24 代，折算约 0.16 ms/代，说明主要来自规则推进"——**这是错的**。
  > 按同样口径相除应当是 `2.4 ms/帧 ÷ 0.229 代/帧 ≈ 10.5 ms/代`，与规则成本（0.2 ms/代）
  > 相差近两个数量级，本身就说明这个折算没有意义：分子是含限帧等待的帧间隔，分母很小，
  > 相除不构成任何成本量。该结论已删除。
- **没有**拆分规则推进 / 布局 / 绘制的占比。**分项成本仍然未知**，因此**不作任何归因**。
- 开发版构建，不是发布版。

|---|---|
| 网格重绘的单独耗时 | **未测**。重绘在面板更新阶段执行；需 Unity Profiler 采样 |
| 布局 / 绘制的占比拆分 | **未测**。因此**不能**断言该优化哪一段 |
| 发布版（非开发版）性能 | **未测**。探针受 `#if DEVELOPMENT_BUILD` 保护，发布版不含它 |

**因此 §6 的任何优化仍不应实施。**

### 5.6 结论

1. **吞吐量约 7,600 万格/秒**（512×512、固定边界，独立工具）。大棋盘上每格成本稳定在 ~13 ns。
2. **环绕边界吞吐下降 39.5%**（512×512：76.2 M → 46.1 M 格/秒）。**换算成每代耗时则是增加 65.4%**（3.442 ms → 5.692 ms）。两个数字描述同一现象、方向相反，引用时必须说明用的是哪一个。
3. **小棋盘单位成本更高**：96×64 只有 29.9 M 格/秒，瓶颈是调用开销而非数据规模。
4. **规则推进的绝对成本很低**：独立工具 0.206 ms/代（96×64 固定边界）；
   编辑器内的 **SYNTHETIC 微基准**在多次运行中给出 0.14–0.23 ms/代（见 §5.3，
   该数字含同帧复用 deltaTime 与 `SendMessage` 派发开销，**不是真实演化采样**）。
   两者同量级，说明规则内核在两个运行时下成本相近。
5. **Player（开发版）中暂停约 8.5 ms/帧，演化中约 10.6–10.9 ms/帧**（帧率上限 120、关垂直同步）；
   最差帧暂停 36.7–48.9 ms、演化 22–23 ms；期间确认推进了 50–52 代。

**分项成本仍然未知**，因此**不对"该优化哪一段"作任何判断**。第 5 条测的是整帧间隔，
不含各段占比；把它与第 4 条的规则成本相减或相除都得不出有意义的量（理由见 §5.4）。

## 6. 若需进一步优化（进阶要求的方向）

按"收益/成本"排序，供后续扩展参考：

### 6.1 消除环绕边界的取模（低风险，收益明确）

为棋盘分配 `(W+2) × (H+2)` 的**幽灵边框**，每代结束后把对边数据复制进边框。之后邻居读取无需任何边界判断——热点循环里直接消失一个分支和两次整数除法。

预期：环绕模式吞吐从 46 M 提升到接近固定边界的 76 M（+65%）。

### 6.2 位打包 + 查表（中风险，收益大）

每行用 `ulong` 位平面存储（64 格/字）。计算下一代时，把每个细胞的"左右邻居"通过移位得到，再对**上下各 3 位一列**做查表（8 位索引 → 2 位结果），一次处理 32 格。

- 内存：1/8
- 运算：位运算替代逐格数组访问，通常有 **3–8 倍**提升
- 代价：可读性显著下降，边界处理变复杂

脉冲星这类稀疏样本收益不明显，高密度随机盘面收益最大。

### 6.3 并行化（中风险）

`Step()` 各格之间完全无依赖（数据竞争已被双缓冲消除），天然适合并行：

- **C# `Parallel.For`**：改动最小，但需处理线程池调度开销，小棋盘上反而更慢。
- **Unity Job System + Burst**：`IJobParallelFor` 按行分块，配合 Burst 编译可接近 SIMD 性能。代价是引入 `NativeArray`，与当前纯 C# 设计冲突（会破坏第 2.2 节的解耦）。

### 6.4 GPU Compute Shader（高风险，收益最大）

把棋盘作为纹理/RWStructuredBuffer，一个线程算一个细胞（或一格 4 个），全部并行。百万格规模下可达数十倍提升。

代价：需要异步回读（GPU→CPU）做统计，会引入延迟；且样本编辑的即时性下降。

### 6.5 当前实现的取舍说明

本项目**没有**实施上述优化，理由是刻意的：

1. 规则推进本身的成本已经很低（独立工具 0.206 ms/代，编辑器微基准同量级）。
2. **其余开销的构成尚未测量。** §7 只是结构性观察，没有任何数据显示网格重绘占了整帧的多大比例——所以**不能**说"重绘成本更高"，只能说"规则推进不是瓶颈，其余部分待测"。
3. 过早引入位运算或 Job System 会让规则内核——这个唯一需要被正确性验证的部分——变得难以阅读和测试，而收益尚未被证明存在。

因此本文档**不建议**在缺乏 Profiler 分项数据的情况下上 Burst、GPU 或位打包。§6.1（消除环绕取模）是唯一即便没有 Profiler 也方向明确的一步，因为它针对的是已被实测证实的 39.5% 吞吐损失。

## 7. 渲染：结构性风险（尚未量化）

> **本章描述的是代码结构上的风险，不是已测定的瓶颈。** 没有 Profiler 采样，因此不应把"渲染是真瓶颈"当作结论。

`LifeGridElement.DrawGrid` 每次重绘会为全部 6,144 个细胞**逐个**构建路径并填充：

```csharp
for (int y = 0; y < simulation.Height; y++)
    for (int x = 0; x < simulation.Width; x++)
    {
        painter.fillColor = ...;     // 每格切换颜色
        FillRect(painter, rect);     // 每格一次 BeginPath/MoveTo/LineTo/Fill
    }
```

一次重绘 = 6,144 次 `BeginPath` + 6,144 次 `Fill`。

**关于触发频率的两点澄清：**

1. `RefreshReadouts()` 在每个演化世代都会调用 `MarkDirtyRepaint()`。**但 `MarkDirtyRepaint()` 只是标记，不等价于立刻执行一次绘制**——真正的 `generateVisualContent` 回调由面板在随后的更新阶段统一执行，同一帧内多次标记会被合并为一次重绘。
2. 因此准确的说法是：**每个包含世代推进的帧最多触发一次全量重绘**。20 代/秒时最多每秒 20 次（若帧率高于 20 fps，多代可能落在同一帧内，标记被合并）。

**改进方向**（按性价比，均需先由 Profiler 确认收益）：

1. **只画活细胞**。死细胞只需背景色：一次背景填充 + 仅对活细胞绘制前景色矩形。脉冲星这类稀疏样本（48 个活细胞）下绘制次数从 6,144 降到 48，**工作量约为 1/128，即减少约两个数量级**（不是三个）。高密度随机盘面收益小得多，因为活细胞比例高。
2. **合并路径**。所有活细胞放在一个 `BeginPath` 内用多个子路径 + 一次 `Fill`，避免逐格切换绘制状态。
3. **降到纹理更新**。把棋盘写进一张 `Texture2D` 并整块上传，由 shader 放大绘制。这是最终形态，也是 6.4 节 GPU 方案的自然搭配。
4. **按需重绘**。暂停时不应重绘；仅在世代真正推进或用户编辑后重绘。

**外观约束（必须保留）**：死细胞的网格底纹是当前视觉语言的一部分（暗色屏幕上的格线感）。若采用第 1 条优化，**不能用"整块纯色背景"取代它**——需要保留死细胞的格线绘制（例如用一次合并路径画完所有格线），只把逐格的颜色切换去掉。否则界面会退化成纯黑底 + 亮点，丢掉终端仪表的质感。

**量化前置条件**：上述收益均为结构性推断。落地前应使用 Unity Profiler 分别采样「规则推进」「网格重绘」「UI 布局」三段的耗时与 GC 分配，再决定改哪一段。

## 8. 测试策略

验证方式分三层，各自回答不同的问题：

| 层次 | 手段 | 回答的问题 |
|---|---|---|
| 引擎正确性 | 与独立参考实现比对随机盘面 | 规则实现对不对？ |
| 样本正确性 | 断言每个样本的周期与种群变化 | 样本是不是它声称的东西？ |
| 界面正确性 | PlayMode 测试驱动真实控件与布局 | 界面能不能用、会不会被裁切？ |

第一、二层的实现：

- **EditMode 测试**（`Assets/Tests/EditMode/`，24 项）：`unity test . --mode EditMode`，约 0.1 秒。参考实现写在测试文件内，**刻意不复用被测代码**——否则同一个 bug 会在两边同时出现，测试通过但毫无意义。
- **独立校验工具**（`.verify/`）：直接链接 `Assets/Scripts` 的真实源码，用于基准测试、RLE 解码、批量样本校验。

**两组随机盘面测试的规模不同，勿混为一谈：**

| 位置 | 盘面数 | 尺寸范围 | 边界 |
|---|---|---|---|
| `.verify -- rules`（独立工具） | 400 | 1×1 – 9×9 | 固定 200 + 环绕 200 |
| EditMode `Step_MatchesIndependentReferenceOnRandomBoards` | 200 | 1×1 – 12×12 | 固定 100 + 环绕 100 |

两者使用不同的随机种子，且各自与**自己文件内的**参考实现比对——参考实现被写了两遍，这是有意的重复，用来降低"两边同时犯错"的概率。

### 8.1 "周期 = N" 的正确断言方式

必须同时断言**准点复原**与**中途不提前复原**。若只断言"第 N 代等于第 0 代"，一个周期为 1 的错样本也可能碰巧在第 3 代相等：

```csharp
for (int generation = 1; generation < pattern.Period; generation++)
{
    sim.Step();
    Assert.AreNotEqual(initial, Snapshot(sim));   // 不允许提前复原
}
sim.Step();
Assert.AreEqual(initial, Snapshot(sim));          // 必须准点复原
```

飞船另有专门的"不提前回到绝对位置"断言（`Spaceships_DoNotRepeatInPlaceAtAnySmallerPeriod`），因为飞船永远不会原地复原，只比较原地状态会漏掉错误周期。

### 8.2 校验工具本身也要被证伪

一个不会失败的校验器毫无价值——如果 `Analyze()` 恒返回"通过"，那么文档里所有"已验证"的说法都是空的。因此 `.verify` 提供 `selftest` 子命令，故意喂给它**错误的声明**，并要求它必须拒绝：

```powershell
dotnet run --project .verify/Verify.csproj -c Release -- selftest
```

覆盖 5 种谎言（稳定态声明为振荡器、振荡器声明为稳定态、周期值写错、飞船声明为原地振荡器等）。若其中任何一条被"接受"，`selftest` 以非 0 退出。

所有校验子命令都把结论传递到**进程退出码**，否则自动化流水线会把"打印了失败"当成成功：

| 子命令 | 含义 | 退出码 |
|---|---|---|
| （默认） | 校验 8 个样本 | 0 全部符合 / 1 有偏差 |
| `rules` | 规则引擎 vs 参考实现 | 0 通过 / 1 有失败 |
| `probe` | RLE 样本周期 | 0 全部符合 / 1 有偏差 |
| `bench` | 性能基准 | 0 正常 / 1 有棋盘死亡（该次测量作废）|
| `selftest` | 证伪校验器自身 | 0 全部拒绝 / 1 漏放 |
| 未知子命令 | 用法错误 | 2 |
