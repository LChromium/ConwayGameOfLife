# 技术分析

Conway's Game of Life 的规则本身只有两句话，真正的工程问题在于：**如何保证规则实现正确**，以及**如何在可接受的时间内推进尽可能多的世代**。本文围绕这两点展开。

---

## 1. 规则与计算模型

### 1.1 规则定义

生命游戏是二维二值元胞自动机。每个细胞的状态由"上一代"的 8 邻域决定：

| 当前状态 | 活邻居数 | 下一状态 | 名称 |
|---|---|---|---|
| 死 | 3 | **活** | 诞生 (Birth) |
| 活 | 2 或 3 | **活** | 存活 (Survival) |
| 活 | 0、1 | 死 | 孤独 |
| 活 | 4–8 | 死 | 拥挤 |

记作 **B3/S23**。注意"活 + 2 邻居"与"活 + 3 邻居"都是存活，因此判定式可合并为：

```
next_alive = (neighbours == 3) || (alive && neighbours == 2)
```

这正是 `LifeSimulation.Step()` 中使用的形式。

### 1.2 同步更新（Double Buffering）——最容易写错的地方

所有细胞必须**同时**基于同一代数据计算。若原地更新，先算完的细胞会污染后算细胞所读到的邻居值，产生难以察觉的错误。

因此本实现使用两块缓冲区：读 `current`、写 `next`，整代算完后交换引用。

```csharp
(current, next) = (next, current);   // 元组交换，交换的是引用，不是数据
```

工程上的关键收益：**每代零堆分配**。若每代 `new byte[]`，1024×1024 的棋盘每代要分配 1 MB，GC 压力会直接体现在帧时间抖动上。这里缓冲区只分配一次并复用。

### 1.3 边界条件

| 模式 | 语义 | 实现 |
|---|---|---|
| 固定边界 | 网格外视为永久死亡 | 越界邻居直接跳过 |
| 环绕边界 | 环形拓扑，对边相接 | `(n + size) % size` |

两者对同一个盘面会产生不同演化结果，测试 `WrapEdges_ProducesDifferentResultFromFixedBoundary` 对此做了断言。

## 2. 数据结构选型

### 2.1 为什么用 `byte[]` 而不是 `bool[,]`

| 方案 | 内存 / 格 | 邻居读取 | 说明 |
|---|---|---|---|
| `bool[,]` | 1 B | 多维索引，边界检查开销较大 | C# 中 `bool` 实际占 1 字节 |
| `bool[]`（手动索引）| 1 B | `y*W+x` | 与 `byte[]` 等价 |
| **`byte[]`（本实现）** | **1 B** | `y*W+x`，一维连续 | 可整块 `Array.Clear`，便于后续向量化 |
| `BitArray` / 位平面 | 1/8 B | 需要移位与掩码 | 内存减少 8 倍，但单格读写变慢 |

选择 `byte[]` 的理由：**为后续优化留路**。一维连续数组可被 JIT 边界检查消除（BCE）优化、可被 SIMD 向量化、也可整块内存复制。当前实现尚未用到位打包，但数据布局不阻碍这一步。

索引统一为 `y * Width + x`——**行主序**。这意味着同一行的细胞在内存中相邻，遍历时缓存局部性最好。`Step()` 的循环外层是 `y`、内层是 `x`，与内存布局一致。

### 2.2 为什么 `LifeSimulation` 不依赖 `UnityEngine`

`LifeSimulation.cs` 只 `using System;`。带来的实际好处：

1. **可在 Unity 之外运行**。本仓库的 `.verify/` 工程直接链接这份源码，用 `dotnet run` 做基准测试与规则校验，无需启动编辑器（启动 Unity 做一次基准测量是分钟级的，`dotnet run` 是秒级的）。
2. **EditMode 测试运行快且稳定**。23 个测试总耗时约 0.1 秒，没有场景加载、没有帧循环。
3. **职责清晰**：规则引擎是纯函数式的状态机，表现层（UI Toolkit）与它解耦。

这条边界是刻意设计的，不是偶然结果。

## 3. 样本（Pattern）的正确性来源

题目要求"两种稳定、两种振荡、两种循环震荡"。样本本身是数据，但**数据也会错**——这一点在本项目中真实发生过，值得记录下来。

### 3.1 一次真实的纠错

最初凭记忆手写了脉冲星（Pulsar）的坐标，并用自制的探针程序测量周期。结果：

```
[FAIL] PULSAR (candidate)  pop 28  UNEXPECTED: declared period 3, measured none
```

也就是说，那串坐标**根本不是脉冲星**——它演化到别的东西上去了，40 代内没有回到初态。

随后做了两件事：

1. **先验证测量工具本身**。写了一份独立的 B3/S23 参考实现，在 400 个随机盘面（含 1×1 到 12×12 各种尺寸、两种边界）上与 `LifeSimulation.Step()` 逐格比对——**0 处不一致**。这排除了"引擎有 bug 导致测不出周期"的可能。
2. **不靠记忆，改用权威 RLE**。从 [copy.sh/life](https://copy.sh/life/) 取得标准 RLE，写了个 RLE 解码器（`.verify/Rle.cs`）来生成坐标，而不是手工转录。

结果：

```
[OK] PULSAR          cells= 48 period=3  (expected 3)   populations: 48,56,72,48,...
[OK] PENTADECATHLON  cells= 12 period=15 (expected 15)  populations: 12,22,18,40,...
```

48 个细胞、周期 3、种群在 48→56→72 之间循环——与脉冲星的已知特征完全吻合。

> **教训**：当测量结果与预期不符时，先怀疑被测对象、再怀疑测量工具，最后才怀疑"预期"本身。而验证测量工具的办法，是用一个**独立实现**去交叉验证，而不是重复运行同一个实现。

### 3.2 最终样本集

| 样本 | 分类 | 周期 | 细胞数 | 首代种群序列 |
|---|---|---|---|---|
| 方块 BLOCK | 稳定状态 | 1 | 4 | 4,4,4,... |
| 蜂巢 BEEHIVE | 稳定状态 | 1 | 6 | 6,6,6,... |
| 闪烁器 BLINKER | 振荡状态 | 2 | 3 | 3,3,...（形态在横竖间切换）|
| 蟾蜍 TOAD | 振荡状态 | 2 | 6 | 6,6,... |
| 脉冲星 PULSAR | 循环震荡 | 3 | 48 | 48,56,72,48,... |
| 十五周期振荡器 PENTADECATHLON | 循环震荡 | 15 | 12 | 12,22,18,40,18,... |
| 滑翔机 GLIDER | 飞船 | 4 | 5 | 平移 (1,1)/周期 |
| 轻型飞船 LWSS | 飞船 | 4 | 9 | 平移 (−2,0)/周期 |

"循环震荡"与"振荡状态"的区别被落实为**周期长度**：周期 2 归入 `Oscillator`，周期 ≥ 3 归入 `PeriodicOscillator`。这个区分不是文字游戏——脉冲星在第 1、2 代形态与细胞数都不同（56、72），到第 3 代才复原，与闪烁器"只有两种形态来回切"有本质差异。测试 `EveryPattern_HasCellsAndConsistentPeriod` 强制这条分类约束成立。

### 3.3 振荡器与飞船的判定差异

两者都"周期性复原"，但飞船的包围盒会整体平移。判定方式因此不同：

- **振荡器**：连续两代以上，包围盒**中心**必须不变。
- **飞船**：经过一个周期后，包围盒中心位移非零，且细胞数不变。

测试 `PeriodicOscillators_StayInPlace` 比较的是包围盒中心而非左上角。原因是振荡器的包围盒尺寸会随形态变化（脉冲星第 1 代会长出新的边），此时左上角坐标会移动，但**中心**不动。用左上角判定会产生假阳性。

## 4. 复杂度分析

设棋盘宽 `W`、高 `H`。

| 操作 | 时间复杂度 | 空间复杂度 | 说明 |
|---|---|---|---|
| `Step()` | O(W·H) | O(1) 额外 | 每格固定读 8 邻居，与棋盘大小无关 |
| `IsAlive` / `SetCell` | O(1) | — | 一次数组索引 |
| `LoadCentered` | O(n + W·H) | O(1) | n 为样本细胞数；`Clear()` 是 O(W·H) |
| `Randomize` | O(W·H) | — | 每格一次随机数 |
| 整块缓冲区 | — | O(W·H) | 两块 `byte[]` |

**核心结论：`Step()` 是 O(W·H)，且每格的常数因子固定为 8 次邻居读取。** 也就是说，总工作量 = 格子数 × 世代数，与细胞密度无关。这是朴素实现的固有特性——包括大量死细胞也在被遍历。

`Step()` 每格的实际操作序列：

```
1 次邻居循环（8 次迭代）
  ├─ 边界处理（取模或跳过）
  ├─ 1 次索引计算 y*W+x
  └─ 1 次数组读取
1 次自身状态读取
1 次规则判定
1 次写入 + 1 次累加
```

值得注意的开销：**环绕边界的取模运算**。`%` 在 x86 上是几十个周期的整数除法，代价远高于一次数组读取。实测数据印证了这一点（见下节）。

## 5. 性能实测

### 5.1 测量方法

用 `.verify/Bench.cs`，`Release` 配置、单核、先预热 30 代再计时：

```powershell
dotnet run --project .verify -c Release -- bench
```

### 5.2 结果

| 棋盘 | 边界 | 世代数 | 总耗时 | 每代 | **格/秒** |
|---|---|---|---|---|---|
| 96×64 | 固定 | 400 | 82.3 ms | 0.206 ms | 29.9 M |
| 96×64 | 环绕 | 400 | 123.3 ms | 0.308 ms | 19.9 M |
| 256×256 | 固定 | 400 | 382.5 ms | 0.956 ms | 68.5 M |
| 256×256 | 环绕 | 400 | 603.4 ms | 1.509 ms | 43.4 M |
| 512×512 | 固定 | 120 | 413.1 ms | 3.442 ms | 76.2 M |
| 512×512 | 环绕 | 120 | 683.1 ms | 5.692 ms | 46.1 M |
| 1024×1024 | 固定 | 60 | 897.7 ms | 14.961 ms | 70.1 M |
| 1024×1024 | 环绕 | 60 | 1410.9 ms | 23.515 ms | 44.6 M |

### 5.3 结论

1. **吞吐量约 7,000 万格/秒**（512×512、固定边界，76.2 M cells/s）。大棋盘上每格成本稳定在 ~13 ns，说明缓存局部性良好、未出现明显的内存带宽瓶颈。
2. **环绕边界慢约 41%**：512×512 从 76.2 M 降到 46.1 M。代价来自 8 次邻居读取各做两次取模。这不是理论猜测，是实测差异。
3. **小棋盘单位成本更高**：96×64 只有 29.9 M cells/s。原因是固定开销（方法调用、循环建立）在总时间中占比更大，说明该规模下瓶颈是调用开销而非数据规模。
4. **对交互式使用绰绰有余**：程序默认 96×64 = 6,144 格，每代 0.21 ms。即使 20 代/秒也仅占 0.4% 的帧预算。

**换句话说：当前规模下性能不是瓶颈，瓶颈在别处**（渲染，见下节）。这个判断很重要——在没有测量的情况下盲目优化规则内核，是在解决一个不存在的问题。

## 6. 若需进一步优化（进阶要求的方向）

按"收益/成本"排序，供后续扩展参考：

### 6.1 消除环绕边界的取模（低风险，收益明确）

为棋盘分配 `(W+2) × (H+2)` 的**幽灵边框**，每代结束后把对边数据复制进边框。之后邻居读取无需任何边界判断——热点循环里直接消失一个分支和两次整数除法。

预期：环绕模式吞吐从 46 M 提升到接近固定边界的 76 M（+65%）。

### 6.2 位打包 + 查表（中风险，收益大）

每行用 `ulong` 位平面存储（64 格/字）。计算下一代时，把每个细胞的"左右邻居"通过移位得到，再对**上下各 3 位一列**做查表（8 位索引 → 2 位结果），一次处理 32 格。

- 内存：1/8
- 运算：位运算替代逐格数组访问，通常有 **3–8 倍**提升
- 代价：可读性显著下降，边界处理变复杂

脉冲星这类稀疏样本收益不明显，高密度随机盘面收益最大。

### 6.3 并行化（中风险）

`Step()` 各格之间完全无依赖（数据竞争已被双缓冲消除），天然适合并行：

- **C# `Parallel.For`**：改动最小，但需处理线程池调度开销，小棋盘上反而更慢。
- **Unity Job System + Burst**：`IJobParallelFor` 按行分块，配合 Burst 编译可接近 SIMD 性能。代价是引入 `NativeArray`，与当前纯 C# 设计冲突（会破坏第 2.2 节的解耦）。

### 6.4 GPU Compute Shader（高风险，收益最大）

把棋盘作为纹理/RWStructuredBuffer，一个线程算一个细胞（或一格 4 个），全部并行。百万格规模下可达数十倍提升。

代价：需要异步回读（GPU→CPU）做统计，会引入延迟；且样本编辑的即时性下降。

### 6.5 当前实现的取舍说明

本项目**没有**实施上述优化，理由是刻意的：`Step()` 每代 0.2 ms，而 UI 重绘的成本远高于此。在 6.2 节之前先做 6.1（消除取模）是唯一性价比明显的一步。过早引入位运算或 Job System 会让规则内核——这个唯一需要被正确性验证的部分——变得难以阅读和测试，而收益在当前规模下不可见。

## 7. 已知性能问题：渲染

**当前真正的瓶颈在渲染层，不在规则层。**

`LifeGridElement.DrawGrid` 每次重绘会为 6,144 个细胞**逐个**构建路径并填充：

```csharp
for (int y = 0; y < simulation.Height; y++)
    for (int x = 0; x < simulation.Width; x++)
    {
        painter.fillColor = ...;     // 每格切换颜色
        FillRect(painter, rect);     // 每格一次 BeginPath/MoveTo/LineTo/Fill
    }
```

一次重绘 = 6,144 次 `BeginPath` + 6,144 次 `Fill`。而 `RefreshReadouts()` 在每一个演化世代都会调用 `MarkDirtyRepaint()`，因此**每代触发一次全量重绘**。

再加上 `Redraws` 的触发频率随速率滑条提高，20 代/秒时是每秒 20 次全量重绘。

**改进方向**（按性价比）：

1. **只画活细胞**。死细胞只需要背景色，用一次背景填充 + 仅对活细胞绘制前景色矩形。稀疏样本（脉冲星 48 格）下工作量从 6,144 降到 48 次，三个数量级。
2. **合并路径**。所有活细胞在一个 `BeginPath` 内用多个子路径 + 一次 `Fill`，避免逐格切换绘制状态。
3. **降到纹理更新**。把棋盘写进一张 `Texture2D` 并整块上传，由 shader 放大绘制。这是最终形态，也是 6.4 节 GPU 方案的自然搭配。
4. **按需重绘**。暂停时不应重绘；仅在世代真正推进或用户编辑后重绘。

## 8. 测试策略

验证方式分三层，各自回答不同的问题：

| 层次 | 手段 | 回答的问题 |
|---|---|---|
| 引擎正确性 | 与独立参考实现比对随机盘面 | 规则实现对不对？ |
| 样本正确性 | 断言每个样本的周期与种群变化 | 样本是不是它声称的东西？ |
| 交互正确性 | 手动运行 | 界面能不能用？ |

第一、二层的实现：

- **EditMode 测试**（`Assets/Tests/EditMode/`）：23 个测试，`unity test --mode EditMode` 运行，约 0.1 秒。参考实现写在测试文件内，**刻意不复用被测代码**——否则同一个 bug 会在两边同时出现，测试通过但毫无意义。
- **独立校验工具**（`.verify/`）：直接链接 `Assets/Scripts` 的真实源码，用于基准测试、RLE 解码、批量样本校验。

第二层测试的一个设计要点：断言**"恰好"**在声明周期复原，并额外断言中途**没有提前**复原。若只断言"第 N 代等于第 0 代"，那么一个周期为 1 的错样本也可能碰巧在第 3 代相等。`Oscillators_ReturnToTheirExactShapeAfterTheirPeriod` 中的循环：

```csharp
for (int generation = 1; generation < pattern.Period; generation++)
{
    sim.Step();
    Assert.AreNotEqual(initial, Snapshot(sim));   // 不允许提前复原
}
sim.Step();
Assert.AreEqual(initial, Snapshot(sim));          // 必须准点复原
```

这样才真正锁定了"周期 = N"这个语义。
