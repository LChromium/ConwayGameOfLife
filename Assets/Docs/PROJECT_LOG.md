## R5 · 2026-09-13 — 实机画面验收与真实性能采样

**起点**：第三轮评审认定核心逻辑与测试体系已达可靠水平，剩下两项前置条件：**一次真实画面验收**与**一次真实性能采样**。本轮只做这两项，并暂停 Burst / GPU / 位打包 / 新玩法。

### 关键认识：编辑器的游戏视图无法被强制成目标分辨率

最初的计划是在 Editor 里把 Game View 调到 1280×720 与 1920×1080 再截图。
实测发现**行不通**：Game View 的尺寸受停靠布局约束，用内部 `GameViewSizes` API 也改不动，
实际渲染分辨率仍是 2560×1440。因此改为**构建 Windows Player**，用
`-screen-width / -screen-height` 启动——那是唯一拥有真实目标分辨率的地方。

为此新增两件工具（都是为验收服务，不是产品功能）：

| 工具 | 位置 | 作用 |
|---|---|---|
| `CaptureLayoutTool` | `Assets/Editor/` | 在编辑器内请求指定尺寸并截图（能力受限，保留作为诊断）|
| `RuntimeLayoutProbe` | `Assets/Scripts/` | Player 加 `-lifeLayoutProbe` 启动时测量布局、截图、采样 240 帧，并**用 `PanelScreenFit` 预测值做交叉验证** |

`RuntimeLayoutProbe` 用 `#if DEVELOPMENT_BUILD || UNITY_EDITOR` 包裹，不会进入 release 构建。

### 实机测量结果

| 指标 | 1280×720 | 1920×1080 |
|---|---|---|
| 可见设计空间 | 1600×900 | 1600×900 |
| **PanelScreenFit 预测 vs 实测偏差** | **0.00 / 0.00** | **0.00 / 0.00** |
| 布局 | 两栏（compact 关闭）| 两栏（compact 关闭）|
| 网格高度 | 546 px | 544 px |
| 平均帧 / 帧率 | 6.6 ms / 152 fps | 6.2 ms / 160 fps |

**第 2 行关闭了 R4 遗留的问题**：此前 `PanelScreenFit` 只与自身单测对齐，
从未与引擎真实的 `ScaleWithScreenSize` 行为比对过。现在 Player 在两种分辨率下
实测面板尺寸与纯函数预测**逐位相同**。

### 画面验收发现并修复的真实缺陷

第一次 720p 截图（compact 布局）暴露出两个肉眼可见的问题：

1. **网格只占显示区上部一小块，下方留出大片空白** —— `.display` 仍是 `flex-grow: 1`，
   把工作区的剩余高度全部吃掉，而网格自身并不增长。
2. **样本档案被压成一行半，滚动条挤在最右侧** —— 剩余空间被 display 抢走后，列表只剩约 88px。

修复后又发现更根本的问题：**compact 断点的阈值本身是错的**。

- R4 用的 `SideBySideContentHeight = 949` 来自一次 900 高面板的**实测渲染高度**。
  但那是"面板多高、子元素就长多高"的结果，**不是布局的最小需求**。
  真实的垂直下限是网格 96 + 读数 62 + 屏幕栏 30，另一列是档案 130 + 96。
- 于是 16:9 视口被误判为"装不下"，全部切进 compact 布局——而实际上两栏布局在 900 高度下
  **绰绰有余**（改回两栏实测：display 653px、grid 546px、library 236px，页脚 886 < 900，全部可见）。
- 阈值改为 `DesignWidth = 1100`、`SideBySideContentHeight = 640`，并在单测中要求
  **所有目标分辨率保持两栏**，同时保留"极小面板仍会堆叠"的用例，确保回退路径不是死代码。

**这次是我自己把"测得的值"当成了"需要的值"** —— 与 R3 的 0.231/0.235 数字混用是同一类错误。

### 本轮最重要的发现：16:10 参考分辨率让 16:9 窗口永远装不下

评审要求"不能靠持续压缩棋盘解决布局"。追查后找到真正的根因：

面板可见高度（`MatchWidthOrHeight`，match=0.5）对 **1440×900（16:10）** 参考分辨率恒为约 854 单位，
**无论屏幕多大**——因为 1280×720 相对参考偏宽、1920×1080 相对参考偏高，几何平均后落在同一处。

```
参考 1440x900： 1280x720 → 可见面板 1518x854 ; 1920x1080 → 1518x854 ; 两者都装不下 949 的内容高度
参考 1600x900： 1280x720 → 可见面板 1600x900 ; 1920x1080 → 1600x900 ; 与设计尺寸一致
```

**修复**：把 `PanelSettings.referenceResolution` 从 1440×900 改为 **1600×900（16:9）**，与项目实际被验收的
分辨率同形。这不是"压缩棋盘"，而是消除了纵横比错配造成的浪费。

### 断点从"看起来需要"变成"推导出来"

评审指出"不要默认 USS 支持媒体查询"——确实不支持，没有 `@media`、也没有基于宽度的选择器。
因此断点必须由代码监听 `GeometryChangedEvent` 切换样式类。为避免它变成拍脑袋的魔数，
新增 [`PanelScreenFit.cs`](../Scripts/PanelScreenFit.cs) 把面板缩放数学抽成**纯函数**，并由单测覆盖：

- `ScaleFactor / VisiblePanelSize / FitsVertically`：**跨分辨率可验证，不需要改变窗口大小**
- 断点条件（`width < 1500 || height < 935`）在 1280×720 / 1920×1080 / 2560×1440 为真，在 1440×900 / 1920×1200 为假——**由测试断言，不是注释**
- 高度阈值取 935 而非实测的 949：靠 `949 < 949` 判定布局没有余量，舍入会决定结果

调试过程中出现过的三次阈值修正（1600 → 1500 → 935）都是**测试先失败、再按实测定值**，不是试出来的。

### 新增张力

**T7 — 1280×720 下面板高度是硬约束（已量化，未完全解决）**

测量得到的完整高度分解（面板空间）：

```
panel 982      header 63      machine 849      footer 37
machine 内部：top-line 29 + display 734 + controls 47 = 810（display 由 library 的 734 驱动）
library 内部：section-title + archive-note + scroll 587 + field-label + dropdown
```

- 内容合计 **949px**，超过 900px 参考高度 **49px**。
- `.machine` 的 `min-height: 300px` 是按预算推导的（900 − 32 padding − 100 header/footer − 11 边框 = 778 上限），实际布局远高于此下限，因此**改小下限不产生效果**。
- 已做的缓解：header 72→64、screen-bar 42→30、readouts 82→62、controls 64→48、preset 56→46、容器 padding 缩短、样本列表改为可滚动 `ScrollView`。
- 现状：在 640×480（测试用的 4:3 视口）下实测 machine 底边落在屏幕内（455/480），断言通过；**更矮的窗口会优先挤压装饰性的 footer**。
- **未解决**：真正的响应式（窄屏改为纵向堆叠）需要 USS 断点或运行时切换类名，本轮未做。这是下一阶段"产品化"的前置条件之一。

### 明确记录：不要做的事

评审与本文档一致同意，**现在不要**上 GPU / Burst / 位打包。理由：规则推进每代 0.231 ms，而**渲染成本从未被 Profiler 采样过**。在缺少「规则推进 / 网格重绘 / UI 布局」三段耗时数据之前优化规则内核，是在解决一个尚未被证明存在的问题。

若将来优化绘制，**必须保留死细胞的网格底纹外观**（终端仪表质感），不能简单删掉背景格子。

### T12 — 缩放模型：与文档不符的说法需要收敛（R5 发现，R5c 修正表述）

`PanelScreenFit` 原先实现 uGUI `CanvasScaler` 常见的对数插值
`scale = screenW^m · screenH^(1-m) / (refW^m · refH^(1-m))`。

Player 实测不符合它：600×1000 对 1600×900 参考下，对数式预测面板宽 **929.52**，
而 Player 实际布局为 **807.48**；线性式 `lerp(W/refW, H/refH, match)` 得 0.7431，
600 / 0.7431 = **807.4**，与实测吻合。两式在 16:9 下完全一致，因此此前所有 16:9 样本都没有区分能力。

- **已修正**：实现改为线性模型，三组 Player 实测值钉进单测，并加一项断言要求两式在非 16:9 下显著不同。
- **表述已收敛**：不再写"Unity 官方文档错了"。准确说法是——
  **Unity 6000.6.0f1 + UI Toolkit `PanelSettings`（`ScaleWithScreenSize` +
  `MatchWidthOrHeight`）的实测行为符合线性模型**；
  那个对数描述来自 uGUI `CanvasScaler`，不能直接套到这里，但也不是本文档要推翻的结论。

### T13 — 面板宽度没有下界；断点依据需重新论证（R5 发现，R5c 修正）

R5 曾写下两个错误结论，现均已推翻：

| 当时的说法 | 实际情况 |
|---|---|
| 面板宽度 = `(W + H×16/9)/2` | 错。正确关系是 `scale = (W/1600 + H/900)/2`、`panelW = W/scale` = `2880W/(1.8W+H)` |
| 最小面板宽度 1152（1:1 时），故阈值 ≤1152 永不触发 | **错**。本方已实测竖屏 600×1000 得到 **807.48**，直接反证"1152 是下界" |

**关于 1152，本文档先后给过两个错误解释，现按核对的数学定稿：**

线性模型、match = 0.5、参考 1600×900 下，设长宽比 `a = W/H`，则

```
scale  = (W/1600 + H/900) / 2
panelW = W / scale = 2880a / (1.8a + 1)
```

- **`panelW` 只取决于长宽比，与窗口绝对大小无关**（400×400 与 4000×4000 都得 1152）。
- **1152 就是 `a = 1`（正方形窗口）时的取值**——这是它的真正来源；
  此前先说它"是对数模型下的值"是错的（对数模型 1:1 时给 1200）。
- **`a → 0` 时 `panelW → 0`，所以没有全局下界**。50×1000 只有 87.5，100×1000 只有 170.4。

因此"阈值 ≤1152 永不触发"确实不成立：阈值为 1100 时，任何 `panelW < 1100` 的窄窗口都会触发。
选 1280 的理由不是"唯一可达"，而是**内容所需宽度**（见控制器注释），且它能覆盖竖屏这类真实场景。

**正确性质**：`panelW = 2880W/(1.8W + H)`，`W→0` 时趋于 0，**没有正下界**；
只有 1:1 窗口恰好落在 1152，但它不是全局最小值。

- **断点依据改为从内容论证**：两栏布局需要 display + 定宽 236 的档案 + 间距；
  1280 宽面板下 display 约得 1000，对 96 格宽的棋盘舒适；再窄则网格损失的速度
  超过档案定宽所能解释，此时交由堆叠布局（网格获得整幅面板宽度）更划算。
  注意这**不是**"唯一可达的阈值"——`panelW` 无下界，1100 也能触发。
- 单测新增 `PanelFit_MatchesTheLinearFormulaDirectly`，直接核对公式本身，
  并显式断言"窄窗口给出窄面板、不存在下界"。

**教训**：R5 里我把**对数模型下的推导值**当成了线性模型的性质，还据此宣称某阈值"不可达"（第一次错）；
R5c 复盘时又称 1152"是对数模型下的值"（第二次错，对数模型 1:1 给的是 1200）。
两次都是**凭印象复述数学而没有当场核算**——与本轮的性能换算错误同源。
现已在单测里把该公式固定下来，并在此写明推导过程，避免再次口算。

## 镜链原则

本轮反复出现的失败模式高度一致，可归纳为一条：

> **凡"声称"与"事实"可能分离的地方，都必须让声称变成机器可检查的。**

四种形态，同一个病根：

| 形态 | 本轮实例 | 处方 |
|---|---|---|
| 文档与人脑分离 | 架构图声称"Console 零错误"，实际 11 条 USS 错误 | 把断言写成测试，而不是写成文字 |
| 声明与数据分离 | `LifePattern.Period` 是声明值，可能与实际行为脱节 | 测试遍历 `LifePatterns.All` 断言每个声明 |
| 测试与被测对象分离 | 参考实现若复用被测代码，会同步继承同一个 bug | 参考实现独立重写 |
| 工具与贡献者分离 | `Verify.csproj` 未提交，别人复现不了 README 的命令 | 忽略规则显式化 + 全新检出验证 |

由此得到两条操作准则：

1. **验证工具本身也要被验证。** 本轮 4 次失败中，有 2 次是校验工具的 bug，2 次是断言的错误——被测的规则引擎从头到尾都是对的。当结果与预期不符时，先怀疑测量，再怀疑被测对象，最后才怀疑预期。
2. **可复现性是仓库的属性，不是代码的属性。** 因此每次改动后，判定标准是"在一个空目录里 clone 下来能不能跑通"，而不是"在我机器上能不能跑通"。
