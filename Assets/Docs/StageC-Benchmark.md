# 阶段 C：大棋盘基准

**范围**：只做基准。**不**扩展播种功能，**不**改 CPU 单生成器，**不**做亚像素密度总览
（评审明确：等出现真实显示问题再另行实施），**不**做 GPU 独立噪声（远期可选实验）。
本阶段**不据此指定任何优化方向**——理由见 §9。

规格要求「分别记录生成、上传、演化、显示与内存占用」，因此全文**五个口径分开成表**，
不合并、不相加。合起来看一个数，正是阶段 A 明确拒绝过的那种归因。

## 1. 测量契约

每个数字是什么、包含什么、不包含什么：

| 口径 | 测的代码路径 | 含 | 不含 |
|---|---|---|---|
| **生成** | `LifeNoiseSeeding.Generate`（CPU、托管、同步） | 一次完整噪声盘面 | 上传、演化、显示 |
| **上传** | `ILifeBackend.LoadBoard` | CPU 后端：逐活细胞 `SetCell`（人口增量维护，是应用真实路径）；GPU 后端：暂存 `uint[]` 拷贝 + `ComputeBuffer.SetData` | 噪声生成、传输完成 |
| **演化** | `ILifeBackend.Step` | CPU 单步；GPU 仅提交；GPU **批量推进 N=5 代 + 一次整盘回读，再除以 5** | 初态生成、上传、显示 |
| **显示** | `LifeGridElement.Refresh`；CPU 后端棋盘变化时的整盘复制＋上传；**四个标注场景**的帧间隔、`FrameTimingManager` 帧时间、视口事实 | 提交侧派发＋背景赋值；帧间隔是真实跨墙钟；GPU 帧时间是**整帧**的 GPU 时间 | 演化（帧间隔里除外，并单独报先进了多少代） |
| **内存** | `GC.GetTotalMemory`、`Profiler.*`，以及**按源码列出的**缓冲容量 | 本进程内**多分配一块同尺寸棋盘**并释放的增量；所列缓冲的容量小计 | 内部分配的归因；不是应用存活总量，也不是峰值 |

**四条口径纪律**（前三条例自阶段 A，本轮不放松，第四条是本轮新增）：

1. **GPU「仅提交」不是 GPU 执行时间。** 0.0006–0.0015 ms 是把手上的活交给 GPU 的代价。
2. **批量推进＋回读的数字是摊销值**，含一次整盘回读，回读占比**未分项测量**；
   与 CPU 单步不是同一个操作（CPU 就地算、不回读），**不推导任何 CPU/GPU 加速比**。
3. **`SetData` 不是传输完成时间**，上传数字不构成带宽声明。
4. **帧间隔不是纯计算成本**：关掉 vsync 与限帧只是让它描述工作量而非节拍，
   调度、GC、驱动提交都在里面。

### 2.1 `isDebugBuild` 与构建选项不一致：三类证据，冲突未解决

r2 的记录里 `isDevelopmentBuild`（即 `Debug.isDebugBuild`）对**两个**构建都报 `false`，
而构建选项明确写了 Development。评审要求核对构建日志、产物身份与 BuildReport，
**不能**据此直接认定 Unity 的判据失效。核对的全部结果如下：

| 证据 | 帧时间构建 | 发布构建 |
|---|---|---|
| 构建日志：请求的选项、`BuildReport.summary.options` | 两者都是 `…, Development` | 两者都是 `None` |
| 产物身份：`<product>_Data/Managed` 里的 `.pdb` 数 | **134 个**（166 个 dll） | **0 个**（166 个 dll） |
| 产物身份：`boot.config` 的 `player-connection-*` | 有（`PlayerConnection` 在监听） | 无 |
| 记录字段 `isDevelopmentBuild` | `false` | `false` |
| 记录字段 `frameTimingStatsReported` | `true` | `true` |
| 记录字段 `graphicsDriverMemoryAvailable` | `false` | `false` |

- **能说的**：构建管线确实收到了 Development（日志与 BuildReport 一致），
  产物也带开发构建的标记（134 个 `.pdb`、PlayerConnection 条目）；
  而 `Debug.isDebugBuild` 把两者都报成 `false`，**因此它不是可用的配置判据**。
- **不能说的**：为什么该属性在两个构建上都为 `false`。Unity 6 对 `DEVELOPMENT_BUILD`
  宏给了弃用警告，提示改用 managed code variant 一类指令，但**本报告没有做受控实验**，
  所以只把冲突记为**未解决**，不推断属性的语义。
- **本报告的处理**：记录靠 `dataPath` / `buildGuid` 区分配置，靠各字段自己的
  `*Available` / `*Reported` 说明可用性，不依赖 `isDevelopmentBuild`。

### 2.2 一次真实事故：失焦冻结

第一次批量运行时，有一轮墙钟耗时 **778 秒**，而该阶段内部 5 个采样全部 ≤ 96 ms。
逐阶段计时定位到 `upload-cpu` 阶段被冻结在中间。**原因是窗口失焦**——独立 Player 默认
`Application.runInBackground = false`，失焦即停走，而 `Time.realtimeSinceStartup` 照常计墙钟。
（阶段 A 的 T15 记过同一现象，当时只留下「与失焦相关」的现场观察，没有定因。）
现在基准开跑前强制 `runInBackground = true`，并把 `focused` 写进每条阶段日志。

### 2.3 第二次失焦事故：进程不退出，守卫触发（只影响退出，不影响测量）

r4 的五轮短程重跑中，前四轮自行退出，**发布版 4096² 那一轮没有退出**，被外部
`WaitForExit(180000)` 守卫杀掉。现场核对：

| 证据 | 内容 |
|---|---|
| 该轮记录 | **已完整写出**：`elapsedSeconds: 13.16`，四个场景齐全，`focusedThroughout: false` |
| 该轮阶段日志 | 场景全部跑完、`appended … to …stage-c-bench-r4.jsonl` 之后**再无输出** |
| 进程 | 记录写完后仍存活 **>167 秒**，直到守卫 `Kill()` |
| 对照 | 4096² 帧时间构建那轮同样 `focused=False`：墙钟 54.4 s、记录内 13.1 s；而小尺寸几轮两者之差只有约 6.6 s（启动开销），**多出的约 41 秒无法用启动解释** |

原因是 r3 的探针在 `Application.Quit(0)` **之前**把 `runInBackground` 还原成了运行前的值
（默认 `false`）：失焦的独立 Player 在 `runInBackground = false` 时不走主循环，
`Application.Quit()` 就不保证被处理。**r4 起不再还原**（探针最后一件事就是退出，没有还原的
理由），并在记录里新增 `runInBackgroundRestored: false`、启动时把原值写进日志。

修复后同一批五轮**全部自行退出**（`exit=0`，含发布版 4096²：墙钟 19 s，此前 >180 s 被杀）。
受影响的只是**退出**而不是测量；但为免同一文件混入被杀进程产出的行，r4 在修复后
**用修复后的同一套构建整体重跑了一遍**，修复前那 5 条留在
`Builds/stage-c-bench-r4-prefix.jsonl`（`Builds/` 在 `.gitignore` 内，不随仓库发布）。

## 3. 生成（CPU 噪声）

| 盘面 | fBm 中位 | fBm 吞吐 | 均匀中位 | 均匀吞吐 | fBm 实际密度 | 均匀实际密度 |
|---|---|---|---|---|---|---|
| 256²（65 536） | 35.6 ms | 1.84 M 格/s | 1.1 ms | 60 M 格/s | 0.3189 | 0.3202 |
| 1024²（1 048 576） | 560.3 ms | 1.87 M 格/s | 13.7 ms | 77 M 格/s | 0.3101 | 0.3198 |
| 2048²（4 194 304） | 2 249 ms | 1.86 M 格/s | 55.0 ms | 76 M 格/s | 0.3143 | 0.3200 |
| 4096²（16 777 216） | 8 911 ms | 1.88 M 格/s | 226.9 ms | 74 M 格/s | 0.3197 | 0.3201 |

**fBm 每格成本与尺寸无关**（1.84–1.88 M 格/s，跨 256 倍格数）：纯函数、无分辨率依赖。
1024² 的 560.3 ms 与阶段 B 记录的 528–563 ms 相符，实际密度 0.3101 也与阶段 B 相同。
均匀模式请求 0.32，实测 0.3198–0.3202。

> **4096² 的 8.9 秒是「同步生成函数」的耗时，不是已经测得的交互等待。**
> 真实预览路径还要经过防抖 200 ms、旧任务收尾、后台调度、采纳与上传；
> **端到端等待本阶段没有测**（见 §9），因此这个数字只能读作「生成这一项要多久」，
> 不能读作「用户要等多久」。

- CPU 每格成本恒定（24.7–29.1 M 格/s），与阶段 A 的 38.66 ms @1024² 同一量级（本轮 38.11 ms）。

### 6.4 时钟过载保护与运行状态（r3 修复，r4 收尾）

**机制（评审纠正后的正确描述）。** 控制器每帧只把 `Time.unscaledDeltaTime` 加进
`accumulator` 一次，循环内持续扣减，所以欠账**不是在一帧内滚大的**。真实机制是**跨帧放大**：

```
这一帧算得久  →  下一帧计入更大的时间差  →  试着补算更多代  →  下一帧更久  →  …
```

2048² 的一次 CPU 单步约 150–170 ms、4096² 约 650–790 ms，都远大于 20 代/秒对应的
50 ms 时钟间隔，于是链条一旦启动就持续放大。表现为**长时间无法操作**。
仅凭代码不能说这个循环在数学上永不结束，本报告也不这么说。

**修复**（`LifeTerminalController.Update`）：

- **每帧推进上限 4 代**，并在**步与步之间**检查 6 ms 时间预算——两个上限抓的是两种形状：
  上限抓「合法但欠了很多代」的快时钟，预算抓「一步就很贵」的慢后端。
- 任一上限触发就**丢弃整代的时钟欠账**（只保留不足一代的余数，时钟相位不漂），
  允许模拟降速；**不跳过任何演化步骤**：发生的每一代都是真实棋盘的真实演化，只是更少。
- **暂停、重置、切换后端都结束整段时钟状态**（`ResetClockState()`；r4 由 `ClearClockDebt` 改名，
  因为它现在不止清欠账）：欠账、**进行中的速率窗口、已发布速率、过载标志**一起清掉。
  欠账不清就会补算旧账；速率与过载标志不清，则从慢 CPU 切到 GPU、或重置后重新运行的头 0.5 秒里，
  界面会继续显示上一段的「实际 N/秒 / 已丢弃欠账」——那描述的是一个已经不存在的运行。
- **界面区分目标、实际与「还没测出」**：新增 `AchievedRateMeasured`。窗口形成前显示
  「演算中 · 采样中」，过载时立即显示「演算中 · 丢弃追赶欠账」（不等 0.5 s 窗口），
  窗口形成后才显示「演算中 · 实际 N/秒」；tooltip 写明目标、实际、窗口长度与过载说明。
  **不再把初始化的 0 当作已测得的低速率。**
- **速率的分子与分母覆盖同一批帧**（r4）：一帧的成本要到**下一帧**的 `delta` 才能看到，
  所以本帧完成的步数留到下一帧再计。窗口是**周期性清零的分段（tumbling）窗口**（0.5 s），
  不是滑动窗口。稳态下两种配对覆盖的是同一批帧、只是错开一帧，差异出现在启动/暂停/突变处。
- 步间耗时改用 `Stopwatch.GetTimestamp()`，运行帧不再每帧分配一个计时对象。

**验证一：可控慢后端（PlayMode，`LifeClockOverloadTests`，5 条）。** 用一个每步固定耗时的
真 CPU 后端包一层，注入到控制器与网格；**时钟一律通过真实按钮驱动**（`▶ 运行` / `Ⅱ 暂停`，
即运行时那条 `NavigationSubmitEvent` 路径），不再用反射写 `running`；setup/teardown 也走
`Stop()` 结束时钟状态，避免继承上一条测试的欠账与速率窗口。

> 现在的问题是「每帧一次、每次很慢」，而不是「一次补很多代」。
> 是否需要把 CPU 演化搬到后台线程，是这条修复之后的**下一个**决定，本阶段不做。

| 显示上传缓冲 | 4 | 262 144 | 4 194 304 | 16 777 216 | 67 108 864 |
| 显示上传暂存 | 4 | 262 144 | 4 194 304 | 16 777 216 | 67 108 864 |
| 基准自己的盘面 + 回读池 | 5 | 327 680 | 5 242 880 | 20 971 520 | 83 886 080 |
| **小计** | **31** | **2.03 MB** | **32.5 MB** | **130 MB** | **520 MB** |

**这是「本探针列出的缓冲的容量小计」，不是应用的存活总量，也不是峰值。** 它漏掉了：
播种会话的两个盘面数组、控制器保存的初态与样本盘面、渲染器的视口纹理等；
同时把只在测量期间存在的回读池算进来了。记录字段名叫 `listedBufferCapacityBytes`
（不是 r1 的 `computedBytes`），并带同样的说明。

> 表里的「CPU 状态 2 B/格」是 `CpuLifeBackend` 的模拟缓冲。**阶段 D 之后终端的 CPU 路径
> 持有 4 块盘面缓冲**（模拟两块 + 显示一块 + 轮换一块），因此实际占用是 **4 B/格**
> （4096² 上约 67 MB，比同步时代多 33.5 MB），见
> [StageD-BackgroundEvolution.md](StageD-BackgroundEvolution.md) §2.1。

### 7.2 实测增量

| 盘面 | CPU 盘面（托管，r2 实测） | GPU 盘面（图形驱动，**r1 实测**） |
|---|---|---|
| 256² | 139 264 B | 786 432 B（≈12 B/格） |
| 1024² | 2 105 344 B | 16 777 216 B（≈16 B/格） |
| 2048² | 8 396 800 B | 67 108 864 B（≈16 B/格） |
| 4096² | 33 422 336 B | 268 435 456 B（≈16 B/格） |
- **CPU 盘面实测 ≈ 2 B/格**（2.00–2.13），与两个 `byte[]` 一致。
- **GPU 盘面驱动增量：r2/r3/r4 的构建里图形驱动计数全是 0**（记录里 `graphicsDriverMemoryAvailable: false`
  并写明原因），因此这一列引自 **r1 记录**（同一段 `MeasureMemory` 代码，只有字段名不同）。
- 能确认的只有两件事：**两份显式状态缓冲合计 8 B/格**（源码）；
  **本机、本 API、本次测量时点，驱动计数增量约 12–16 B/格**。
  **额外部分来源尚未定位**——r1 曾把它写成「两份上传暂存」与「小尺寸共享池」，那两条确定性
  归因已删除，现在记录里是 `driverDeltaMinusStateBuffersBytes` + 「未归因」的说明。
- **托管增量不可作为分配量度**：小尺寸出现负值，且不跟随实际分配的数组。
  r1 曾把它归因于「非压缩 GC 保留大块」；**该机制未经证实，已删除**，
  现在只标注「不可用、原因未确认」（`managedDeltaUsable: false`）。

### 7.3 进程整体（仅供参考，不参与结论）

开发版配置下 `allocatedTotalMB` 166–239 MB（r1）、327–479 MB（r2，构建差异未追），
`reservedTotalMB` 578–839 MB。**这两组数不跨构建比较**，也不用来对账 §7.1 的小计。

## 9. 本阶段**不**得出的结论

- **不指定优化方向。** 五个口径分开记录，但「该优化哪一个」由评审按目标决定；
  本阶段没有做任何优化或前后对比（时钟过载保护是**正确性修复**，不是性能优化）。
- **不声称 CPU/GPU 加速比**；**不把 GPU 仅提交当执行时间**；
  **不分解批量摊销里的回读占比**。
- **不用暂停场景的 GPU 帧时间解释演化**（r1 的这条已删除）。
- **不声称「帧时间与盘面无关」**：只有中位数接近，均值与尾部未归因。
- **不把 8.9 秒当作已测的交互等待**：那是同步生成函数的耗时（§3）。
- **不声称追赶受限就等于单步不卡顿**（§6.4）。
- **不把面板上的自报速率当精确测量**：它是 0.5 秒窗口内按**整代**计数的结果，
  分辨力约 2 代/秒；凡引用它都用同一时刻的完成世代差 ÷ 墙钟并列（§6.2/§6.4）。
- **不做亚像素密度总览**：只给出「4096² 时 98.3% 盘面不可见」这个数字。
- **不改 CPU 单生成器**：生成仍是「CPU 生成一次、批量上传」。

### 交给评审的产品观察

1. **4096² 的 fBm 生成约 8.9 秒**（同步生成函数耗时，不是端到端等待）。评审已指明它是
   后续优化的明确候选，且**先记录真实交互等待与取消响应**再决定手段——本阶段没有测这两项。
2. **4096² 时 98.3% 的盘面不可见**：评审支持随后做**全盘密度总览＋局部细胞观察**
   （总览解决"看不到整个实验"，局部视图保留逐格观察与编辑）。这是**显示能力完善**，
   **不应宣传为演化算法提速**。评审已决定**暂缓**，本轮不做。
3. **CPU 追赶放大已修**（§6.4）。剩下的问题是「每帧一次、每次 206–746 ms 的同步单步」，
   即**单步卡顿**，限制追赶并不能解决它。**是否把 CPU 演化移到后台线程，是这条修复之后的
   下一个决定**（评审已把它排为下一项独立工作，密度总览再往后排）。
   后台演化**不会**自动提高算法吞吐，重点是：暂停/平移/参数操作在计算期间仍可响应；
   **后台独占模拟状态、主线程只接收完整世代、重置或切换后端后旧结果不得覆盖新棋盘**
   ——阶段 B 的请求身份机制正好可以复用。

> **该工作已在阶段 D 实施**，见 [StageD-BackgroundEvolution.md](StageD-BackgroundEvolution.md)
> 与 `stage-c-bench-r5.jsonl`。§6.2/§6.4 里 CPU 后端那一行的帧时间因此只描述**同步时代**：
> r5 记录中同一场景的帧中位从 206.4/739.2 ms 落到 **0.27 ms**，而**整盘上传仍留在主线程**
> （2048² 13.5 ms、4096² 50–56 ms，表现为帧最大 19.7/63–72 ms）。本文件其余结论不变。

### 已知限制

| 限制 | 说明 |
|---|---|
| 单机单配置 | 7800X3D / RTX 4070 Ti / D3D12，一种窗口（视口 615×456）。换机器或换视口，显示一栏会变 |
| 帧时间是「最近的记录」，不是窗口的均匀采样 | 每场景采集调用次数、请求返回上限、有效返回数三个数都给（18–23 有效），不外推 |
| `isDebugBuild` 不是配置判据 | 见 §2.1：与构建日志/产物身份冲突，冲突未解决；记录靠 `dataPath`/`buildGuid` 与各字段可用性区分 |
| 图形驱动内存只有 r1 有 | r2/r3/r4/r5 的构建里计数为 0；§7.2 已标明出处 |
| 大尺寸采样次数少 | 生成与演化：256²/1024² 5 次重复，2048² 3 次，4096² 2 次；批量步数统一 5。数字的 `samples` 与 `batchSteps` 都写在记录里 |
| 托管内存增量不可用 | 见 §7.2，不作为依据 |
| 每帧重绘是人为最坏情况 | 应用实际每代重绘一次；该场景只用来分离「重绘」与「演化」 |
| 自报速率的分辨力约 2 代/秒 | 0.5 秒窗口按整代计数：20 代/秒下是 10%，1.3 代/秒下超过 100%。它与墙钟实测的差都在「一个世代/窗口」内（§6.4） |

| 过载标志的读法在 r5 变了 | 后台后端下时钟每帧都越过间隔并丢弃欠账，标志每帧翻转，末尾单次读数是掷硬币；r5 记录改为给「窗口内是否出现过」（`controllerEverOverloaded`）与出现帧数，旧的 `controllerClockOverloaded` 字段名弃用 |

## 10. 复现

```powershell
# 帧时间构建（构建时打开 enableFrameTimingStats）与发布构建
unity build . --target StandaloneWindows64 -o Builds\LifeTerminal-bench.exe `
    --execute-method ConwayGameOfLife.EditorTools.PlayerBuild.BuildBenchmarkWindows64
unity build . --target StandaloneWindows64 -o Builds\LifeTerminal-release.exe `
    --execute-method ConwayGameOfLife.EditorTools.PlayerBuild.BuildReleaseWindows64

# 全量：五个口径，每个尺寸一个进程；外部超时守卫随进程走，触发即视为失败
foreach ($size in '256x256','1024x1024','2048x2048','4096x4096') {
    $p = Start-Process Builds\LifeTerminal-bench.exe -PassThru -ArgumentList `
        "-screen-width 900 -screen-height 700 -screen-fullscreen 0 -lifeBoard $size -lifeBench"
    if (-not $p.WaitForExit(180000)) { $p.Kill(); throw "guard fired for $size" }
}

# 只重跑受影响的帧场景（r4 用这条；其余口径写成 null 并列进 phasesSkipped）
$p = Start-Process Builds\LifeTerminal-bench.exe -PassThru -ArgumentList `
    "-screen-width 900 -screen-height 700 -screen-fullscreen 0 -lifeBoard 4096x4096 -lifeBench -lifeBenchScenarios frame"
if (-not $p.WaitForExit(180000)) { $p.Kill(); throw "guard fired" }
```
