# 阶段 C：大棋盘基准

**范围**：只做基准。**不**扩展播种功能，**不**改 CPU 单生成器，**不**做亚像素密度总览
（评审明确：等出现真实显示问题再另行实施），**不**做 GPU 独立噪声（远期可选实验）。
本阶段也**不据此指定任何优化方向**——理由见 §7。

规格要求「分别记录生成、上传、演化、显示与内存占用」，因此全文**五个口径分开成表**，
不合并、不相加。合起来看一个数，正是阶段 A 明确拒绝过的那种归因。

---

## 1. 测量契约

每个数字是什么、包含什么、不包含什么：

| 口径 | 测的代码路径 | 含 | 不含 |
|---|---|---|---|
| **生成** | `LifeNoiseSeeding.Generate`（CPU、托管、同步） | 一次完整噪声盘面 | 上传、演化、显示 |
| **上传** | `ILifeBackend.LoadBoard` | CPU 后端：逐活细胞 `SetCell`（人口是增量维护的，这是真实路径）；GPU 后端：暂存 `uint[]` 拷贝 + `ComputeBuffer.SetData` | 噪声生成 |
| **演化** | `ILifeBackend.Step` | CPU 单步；GPU 仅提交；GPU 提交 + 一次整盘回读强制同步 | 初态生成、上传、显示 |
| **显示** | `LifeGridElement.Refresh`、CPU 后端的整盘回读＋上传、真实帧间隔、`FrameTimingManager`、视口事实 | 提交侧派发 + 背景赋值；帧间隔是真实跨帧墙钟；GPU 帧时间是**整帧**的 GPU 时间 | 演化（帧间隔里除外，并单独报告先进了多少代） |
| **内存** | `GC.GetTotalMemory`、`Profiler.*`，以及**按源码算出的**每块缓冲大小 | 在本进程内**多分配一块同尺寸棋盘**并释放的增量；算出来的分解 | 不把 `GC.GetTotalMemory` 与 `Profiler` 两个计数器相加或互相印证 |

**三条口径纪律**（沿用阶段 A 的约定，本阶段不放松）：

1. **GPU「仅提交」不是 GPU 执行时间。** 0.0005–0.002 ms 是把手上的活交给 GPU 的代价。
2. **GPU「提交+同步」是上界**，含执行、同步与一次整盘回读；与 CPU 单步不是同一个操作
   （CPU 单步就地算，不回读），因此**不从中推导任何 CPU/GPU 加速比**。
3. **`SetData` 不是传输完成时间**：它在数据交给驱动后返回，因此上传数字不构成带宽声明。

## 2. 环境与配置（每条记录自带）

| 项 | 值 |
|---|---|
| CPU / GPU / API | AMD Ryzen 7 7800X3D（16 线程） / NVIDIA GeForce RTX 4070 Ti（11994 MB） / Direct3D12 |
| 系统内存 | 31937 MB |

| 构建 | 输出 | `isDevelopmentBuild` | 帧时间 / 显存计数可用 |
|---|---|---|---|
| 主测量构建 | `Builds/LifeTerminal.exe` | true | 是 |

> 原计划让「帧时间构建」提供 GPU 帧时间与显存，结果**两个开发版构建都能提供**，

> 最差 17%（亚毫秒项）。发布构建是额外补的，用来回答「开发版的数字在发布配置下还成立吗」。

### 一次真实事故，以及它怎么被修掉

第一次批量运行时，有一轮墙钟耗时 **778 秒**，而该阶段内部 5 个采样全部 ≤ 96 ms。
加了逐阶段计时后定位到：`upload-cpu` 阶段被冻结在中间。
**原因是窗口失焦**——独立 Player 默认 `Application.runInBackground = false`，
失焦即停走，而 `Time.realtimeSinceStartup` 照常计墙钟。（阶段 A 的 T15 记过同一现象，
当时只留下「与失焦相关」的现场观察，没有定因。）

基准现在开跑前强制 `Application.runInBackground = true`，并把 `focused` 写进每条阶段日志。
修后 8 轮全部 9–32 秒完成，逐阶段日志里只剩 4096² 的 fBm 生成（18 秒，符合预期）。

## 3. 生成（CPU 噪声）

| 盘面 | fBm 中位 | fBm 吞吐 | 均匀中位 | 均匀吞吐 | fBm 实际密度 | 均匀实际密度 |
|---|---|---|---|---|---|---|
| 256²（65 536） | 32.8 ms | 2.00 M 格/s | 0.6 ms | 110 M 格/s | 0.3189 | 0.3202 |
| 1024²（1 048 576） | 531.6 ms | 1.97 M 格/s | 11.6 ms | 90 M 格/s | 0.3101 | 0.3198 |
| 2048²（4 194 304） | 2 161 ms | 1.94 M 格/s | 54.4 ms | 77 M 格/s | 0.3143 | 0.3200 |
| 4096²（16 777 216） | 8 585 ms | 1.95 M 格/s | 212 ms | 79 M 格/s | 0.3197 | 0.3201 |

**fBm 的每格成本与尺寸无关**（1.94–2.00 M 格/s，跨 256 倍格数），这是纯函数、无分辨率依赖的直接结果。
1024² 的 531.6 ms 与阶段 B 记录的 528–563 ms **对得上**，实际密度 0.3101 也与阶段 B 的 0.3101 相同——
同一个生成器、同一组参数，换一个阶段测还是同一个数。

均匀模式请求 0.32，实测 0.3198–0.3202。

## 4. 上传

| 盘面 | CPU `LoadBoard` 中位 | GPU `LoadBoard` 中位 | GPU 吞吐 |
|---|---|---|---|
| 256² | 0.36 ms | 0.13 ms | 492 M 格/s |
| 1024² | 5.25 ms | 0.98 ms | 1 075 M 格/s |
| 2048² | 21.9 ms | 5.27 ms | 796 M 格/s |
| 4096² | 86.2 ms | 22.4 ms | 749 M 格/s |

两者都随格数线性增长。CPU 侧不是 `memcpy`：`LoadBoard` 逐活细胞调 `SetCell`，
因为人口是增量维护的（这是应用真实走的路，不是为基准造的捷径）。
GPU 侧含暂存拷贝与 `SetData`，**不含传输完成**。

## 5. 演化

| 盘面 | CPU 单步中位 | CPU 吞吐 | GPU 仅提交 | GPU 提交+同步 |
|---|---|---|---|---|
| 256² | 2.35 ms | 27.9 M 格/s | 0.0007 ms | 0.025 ms |
| 1024² | 36.7 ms | 28.6 M 格/s | 0.0008 ms | 0.73 ms |
| 2048² | 151 ms | 27.8 M 格/s | 0.0017 ms | 3.51 ms |
| 4096² | 630 ms | 26.6 M 格/s | 0.0012 ms | 20.4 ms |

- CPU 每格成本恒定（26.6–28.6 M 格/s），与阶段 A 的 38.66 ms @1024² 同一量级（本次 36.7 ms）。
- GPU 仅提交**与盘面大小无关**（约 0.001 ms）：一次派发就是一次派发。
- GPU 提交+同步随盘面线性增长，因为**回读整盘**是它的大头；这是上界，不是执行时间。
- **不推导加速比**：两者不是同一个操作，见 §1。

## 6. 显示

### 6.1 重绘路径

| 盘面 | 渲染派发（GPU 后端） | CPU 后端重绘：整盘回读＋上传 |
|---|---|---|
| 256² | 0.0037 ms | 0.40 ms |
| 1024² | 0.0033 ms | 6.08 ms |
| 2048² | 0.0027 ms | 27.7 ms |
| 4096² | 0.0036 ms | 102.6 ms |

**派发成本与盘面无关**：渲染 kernel 写的是视口大小的纹理（615×456），不是盘面大小。
**CPU 后端的重绘成本随盘面线性增长**，因为每次重绘都要把整盘读回来再上传：
4096² 时**一次重绘 102.6 ms**，比一次 CPU 单步（630 ms）小，但已经不是可以忽略的量。
GPU 后端没有这笔开销——kernel 直接读后端的活缓冲。

### 6.2 帧间隔（关 vsync、不限帧）

| 盘面 | 空闲（不重绘） | 每帧重绘 | 运行中（20 代/秒） | 实际达成 | GPU 帧时间 | CPU 帧时间 |
|---|---|---|---|---|---|---|
| 256² | 0.35 ms | 0.34 ms | 0.32 ms | 19.99 代/s | 0.059 ms | 0.30 ms |
| 1024² | 0.35 ms | 0.38 ms | 0.31 ms | 19.99 代/s | 0.058 ms | 0.29 ms |
| 2048² | 0.37 ms | 0.39 ms | 0.32 ms | 20.00 代/s | 0.058 ms | 0.29 ms |
| 4096² | 0.38 ms | 0.42 ms | 0.33 ms | 19.99 代/s | 0.061 ms | 0.30 ms |

**从 256² 到 4096²（格数 ×256），帧间隔与 GPU 帧时间都没有变化。** 原因是同一个：
显示成本由视口决定，不由盘面决定；演化在 GPU 后端上是 0.001 ms 的派发。
「运行中」这一栏还报告了**真正推进了多少代**（每轮 ≥5 代，实测约 40 代），
因为一个没演化的帧间隔说明不了应用的行为。

GPU 帧时间来自 `FrameTimingManager`，是**整帧**的 GPU 时间（含 UI 合成），不是"棋盘渲染成本"。

### 6.3 棋盘大于视口时，看不到的部分就是不显示

| 盘面 | 每格像素 | 可见格数 | 占盘面 |
|---|---|---|---|
| 256² | 1 | 256×256 | **100%**（整盘可见） |
| 1024² | 1 | 615×456 | 26.7% |
| 2048² | 1 | 615×456 | 6.7% |
| 4096² | 1 | 615×456 | **1.67%** |

缩放是**整数**像素/格且**不小于 1**，所以盘面永远不会被降采样：大于视口的棋盘只显示
居中的一块。这是显示路径的既有设计（保证"一个活细胞永远不小于一个像素"），
**本阶段不改它**，只把代价量化出来。

> 这正是评审说的「根据实际显示问题另行实施」里那个"实际显示问题"的候选：
> 4096² 时 98.3% 的盘面不可见。要不要做亚像素密度总览，由评审按这个数字决定。

## 7. 内存

### 7.1 实测增量（多分配一块同尺寸棋盘再释放）

| 盘面 | CPU 盘面（托管） | GPU 盘面（托管） | **GPU 盘面（显存/驱动）** |
|---|---|---|---|
| 256² | 139 264 B | 噪声（见下） | 786 432 B（12.0 B/格） |
| 1024² | 2 105 344 B | 噪声 | 16 777 216 B（16.0 B/格） |
| 2048² | 8 396 800 B | 7 774 208 B | 67 108 864 B（16.0 B/格） |
| 4096² | 33 562 624 B | 33 030 144 B | 268 435 456 B（16.0 B/格） |

- CPU 盘面实测 ≈ **2 B/格**（2.000–2.125），就是两个 `byte[]`（当前 + 下一帧），与 `LifeSimulation` 的字段一致。
- GPU 盘面显存实测 ≈ **16 B/格**＝两个 `ComputeBuffer`（8 B/格）＋驱动为**两次**首次上传各留一份暂存（8 B/格）。
  4096² 的 268 435 456 B 正好是 4 × 67 108 864 B，四份都是 4 B/格——**多出来的两份不是噪声，是构造时 front/back `SetData` 各一次**。
  256² 偏小（12 B/格）：小尺寸的分配落在驱动的共享池里，不单独计价。
- **托管增量不可靠，明确标注**：小尺寸会出现负值（256² 为 −0.5 MB），
  因为 Unity 的非压缩 GC 保留已释放的大块。要读的是显存增量与下面的计算值。

### 7.2 按源码算出的分解（字节）

| 缓冲 | 每格 | 256² | 1024² | 2048² | 4096² |
|---|---|---|---|---|---|
| CPU 状态（`current` + `next`） | 2 | 131 072 | 2 097 152 | 8 388 608 | 33 554 432 |
| GPU 状态（front + back） | 8 | 524 288 | 8 388 608 | 33 554 432 | 134 217 728 |
| GPU 暂存数组（上传 + 回读） | 8 | 524 288 | 8 388 608 | 33 554 432 | 134 217 728 |
| 显示上传缓冲 | 4 | 262 144 | 4 194 304 | 16 777 216 | 67 108 864 |
| 显示上传暂存 | 4 | 262 144 | 4 194 304 | 16 777 216 | 67 108 864 |
| 基准自己的盘面 + 回读池 | 5 | 327 680 | 5 242 880 | 20 971 520 | 83 886 080 |
| **合计** | **31** | **2.03 MB** | **32.5 MB** | **130 MB** | **520 MB** |

进程整体：开发版分配总量 166–239 MB，**显存计数器 224 MB（256²）→ 716 MB（4096²）**。
两端的差值约 492 MB，其中可归因于盘面的是 GPU 状态缓冲 134 MB ＋ 显示上传缓冲 67 MB
＋ 驱动为首次上传保留的暂存；**其余不逐项对账**——没有逐项计数的 API，
硬凑一个等式只会把碎片和驱动池写成假精度。（§7.1 的增量是"再多一块棋盘"，
§7.2 的计算块是"应用自己活着的那几块"，两者是不同的问题。）

## 8. 发布配置交叉检查

所有上表数字都来自**开发版**（与阶段 A 的约定一致）。补一轮发布构建，回答"发布配置下还成立吗"：

| 项（4096²） | 开发版 | 发布版 | 差 |
|---|---|---|---|
| fBm 生成 | 8 585 / 8 650 ms | 8 815 ms | +2% |
| 均匀生成 | 212 / 221 ms | 208 ms | −3% |
| CPU 上传 | 86.2 / 95.6 ms | 88.5 ms | 一致 |
| GPU 上传 | 22.4 / 21.9 ms | 21.1 ms | 一致 |
| CPU 单步 | 630 / 660 ms | 642 ms | 一致 |
| GPU 提交+同步 | 20.4 / 22.0 ms | 17.1 ms | −20% |
| 渲染派发 | 0.0036 ms | 0.0023 ms | 一致 |
| 运行中帧间隔 | 0.33 ms | 0.29 ms | 一致 |
| 实际达成代/秒 | ≈20.00 | 19.99 | 一致 |
| GPU 帧时间 / 显存 | 0.061 ms / 716 MB | **无数据** | 两项只在开发版里有 |

**结论：开发版的数字在发布配置下成立**（量级与趋势一致，差异在几个百分点内；
`gpuSync` 的 −20% 是本表最大的差，而它本来就是上界口径）。这一条不能反过来说：
它只说明"开发版没有把数字变好看"，**不构成发布版性能验收**——发布版没有 GPU 帧时间与显存数据。

## 9. 本阶段**不**得出的结论

- **不指定优化方向。** 五个口径现在是分开的，但"该优化哪一个"要由评审按目标决定；
  本阶段没有做任何优化，也没有做优化的前后对比。
- **不声称 CPU/GPU 加速比**（口径不同，见 §1）。
- **不把 GPU 仅提交当执行时间**。
- **不做亚像素密度总览**：只给出"4096² 时 98.3% 盘面不可见"这个数字。
- **不改 CPU 单生成器**：生成仍是"CPU 生成一次、批量上传"。

### 已知限制

| 限制 | 说明 |
|---|---|
| 单机单配置 | 一台机器（7800X3D / RTX 4070 Ti / D3D12），一种窗口尺寸（视口 615×456）。换机器、换视口，显示一栏的数字会变 |
| GPU 帧时间与显存只在开发版 | 发布版 `FrameTimingManager` 与 `Profiler.GetAllocatedMemoryForGraphicsDriver` 都没有数据，记录里如实写 `null` + 原因 |
| 大尺寸的采样次数少 | 生成与演化：256²/1024² 各 5 次重复（20 步/次），2048² 3 次（5 步/次），4096² 2 次（2 步/次）。每个数字的 `samples` 与 `stepsPerRepeat` 都写在对应记录里，不藏 |
| 两次独立构建的重复性 | 同尺寸、同配置、两次独立构建：多数项差异 ≤10%，最差 17%（出现在亚毫秒项，如 256² 的 GPU 上传 0.13 vs 0.16 ms）。没有做更多轮次，因此这不是置信区间 |
| 托管内存增量噪声大 | 见 §7.1，不作为结论依据 |
| 每帧重绘是人为最坏情况 | 应用实际是每代重绘一次；该分支只用来分离"重绘"与"演化" |

## 10. 复现

```powershell
# 两个开发版配置（第二个构建时打开 enableFrameTimingStats）
unity build . --target StandaloneWindows64 -o Builds\LifeTerminal.exe
unity build . --target StandaloneWindows64 -o Builds\LifeTerminal-bench.exe `
    --execute-method ConwayGameOfLife.EditorTools.PlayerBuild.BuildBenchmarkWindows64

# 发布配置（只用于交叉检查：GPU 帧时间与显存不会有数据）
unity build . --target StandaloneWindows64 -o Builds\LifeTerminal-release.exe `
    --execute-method ConwayGameOfLife.EditorTools.PlayerBuild.BuildReleaseWindows64

# 每个尺寸一个进程：分配器与峰值都是干净的
foreach ($size in '256x256','1024x1024','2048x2048','4096x4096') {
    Builds\LifeTerminal.exe -screen-width 900 -screen-height 700 -screen-fullscreen 0 `
        -lifeBoard $size -lifeBench
}
```

每条记录追加到仓库根目录 `stage-c-bench.jsonl`（10 行：开发版 ×4 尺寸 ×2 构建，发布版 ×2 尺寸）。
Player 日志里的 `[stage-c-bench] phase <名字>: <秒>s focused=<真假>` 是逐阶段时间线，
失焦冻结那种事故就是靠它定位的。
